# MetaZone Admin  (v1.0.0)

Your control panel: users, Premium activation, **limits & offers per plan**, unlimited-Free bonus, payment info,
notices, app version. A static site (no server of its own): it talks to your Supabase project, and **every
action is a database function that only works for accounts listed in `admin_users`** -- hiding a button is
cosmetic, the server refuses everyone else (tested). No secret key is used or needed.

## One-time setup
1. Supabase SQL Editor: run the SQL files `0001…` through `0008…`, then `0010…`, `0011…`, `0012…`, `0013…` and `0014…` **in that order, once each** (0006 = page on/off switches; 0007 = Adobe Tracker joins the page switch; if you already ran 0001–0006, run only 0007 — it is optional, the app works without it) (folder `database/` in this download; it is `supabase/migrations/` in the main MetaZone project).
   > **Migration 0014 has never been executed against any PostgreSQL / Supabase project.** Apply it to a TEST Supabase project first (with its own copy of this folder whose `config.js` points at that test project), run `supabase/tests/test_addon_manager.py` there, and only then consider your real project. Take a backup before running it on a real project. See `CHECKPOINT_HANDOFF.md` (Step 2.6 checklist).
2. Supabase → Authentication → URL Configuration → Redirect URLs: add
   `http://localhost:5173/`   (and, if you host the site, its exact URL, e.g. `https://hasibulnikon.github.io/metazone-releases/admin/`).
3. Make yourself an admin (SQL Editor; sign in to the admin site once first so your account exists):
   ```sql
   insert into public.admin_users(user_id) select id from auth.users where email = 'YOUR_GMAIL@gmail.com';
   ```

## Run it
* On your PC: double-click `run_admin.bat`, then use the page that opens (`http://localhost:5173/`).
* Or host the `MetaZone_admin` folder on GitHub Pages (public repo) -- the page is public but shows nothing without an admin login.

`config.js` holds only the public Supabase URL + publishable key. `vendor/supabase.js` is supabase-js (MIT), bundled so
the site works without any CDN.

## What each page does
* **Overview** -- users (total / active now / today / free / premium / expired / suspended), generations, subscriptions, app versions.
  *Step 22A:* the "Adobe Tracker searches" panel (Overview) and the "Tracker" column (Users) were removed. Overview and Users no longer call `admin_tracker_search_stats()` or read `tracker_searches`; the database objects (0008) are NOT changed or removed in this step and still work for older Admin copies. Browser check (stubbed server, no database): `node test_ui/overview_users.smoke.js`.
* **Users** -- search, Activate / Extend / set expiry / Deactivate Premium, Suspend / Restore, per-user usage + history.
* **Limits & Offers** -- for Free and Premium separately: daily limit, weekly limit, API keys per provider; each one a number or *Unlimited*.
  **Bonus**: unlimited Free generations for 1/3/7/30 days or until a date -- it ends by itself. Advanced: batch size, slot hold time, online threshold.
* **Pages** -- switch each app page (Meta, Image to Prompt, Embed, Prompt-to-Prompt, Batch, Tracker, API Manager) on or off for everyone. For one customer: **Users → Pages** forces a page on or off for that account only (beats the global switch), e.g. a cheaper plan without Batch, or Tracker on for you only while it is off for everyone. Home and Settings are always on.
* **Pages** (v0.9.9.10) is grouped: **Pages** and **Add-on features** (add-on switches; Tracker's row also controls the Adobe Tracker add-on). Same Free / Premium / Everyone switches and per-user exceptions (Users → Pages). Free users still see locked add-ons in the app, with Download disabled.
  *Retired entries (Step 21, migration 0018):* the Converter page row `converter`, the File Converter switches `converter_image` / `converter_video` and the Advanced Embedder switches `embed_vector` / `embed_video` are removed from **Pages** / **Add-on features** by the NEW migration `0018_retire_converter_embedder_entries.sql` (run it after 0017; it is safe to re-run and stops without changes if an add-on release still uses one of these keys). The Core pages `embed` and `tracker` are untouched, and the built-in vector / video embedding needs no switch. A small guard keeps older `0010` / `0012` from re-creating the rows if they are ever re-run. Until 0018 is applied to a Supabase project those rows still show there and have no effect. 0018 has not been run against any database yet.
* **Add-ons** (v0.9.9.10, needs migration 0012) -- releases table (Yank / Restore) and **Publish a new release**: pick the signed `.mzaddon` package and its `release.json` sidecar (`{addon_id, version, seq, channel, size, sha256, feature_key, title, summary, min_core, max_core, notes:{pages,problems,fixes}}`). The panel validates the sidecar, computes the package SHA-256/size in your browser and refuses a mismatch, shows the notes, uploads to the private Storage bucket `addons` with your own admin session (no service key), then calls `admin_publish_addon`. If anything fails after the upload it says so and offers Retry / Remove uploaded file. Published releases are immutable: publish a new version (higher seq) instead. Pure logic is in `addon_logic.js`; test: `node test/addon_logic.test.js`.
* **Premium payment info** -- bKash number, price, contact, instructions shown in the app.
* **Notices** -- shown in the app as a right-to-left ticker under the header (each notice once per day per user, priority first).
* **App version** -- set the latest release + download link; apps on an older version show an update banner.

Apps see changed limits on their next refresh (heartbeat, a few minutes) and always at the start of a batch.

## Updates (v0.9.9.5)
Admin → App version → **Download URL** should be a **direct https link to the installer `.exe`** (for example a GitHub
release asset). The app then downloads it inside its own window (progress + speed) and installs it with the same Inno
installer as before. If the link is a web page instead, the app notices and opens it in the browser, as in earlier versions.

## Look & feel (v0.9.9.6)
Dark, compact, one shared design system: every colour/spacing/radius is a variable at the top of `admin.css` (`:root`), and every page uses the same components (buttons, inputs, badges, tables, panels, nav, modal). Branding lives in `assets/` (`assets/README.md` lists the files to replace). This release changed presentation only: no SQL migration, no change to what any admin action does.

## Task 2 additions (needs migration 0013)

* **Pages** - Home and Settings are protected ("Always on (protected)"); the server refuses to switch them off. The "Everyone" master switch now beats a per-user ON (OFF = off for all). A "Last changed" column and a **Recent changes** list (who/what/when) were added.
* **Add-ons** - each add-on has an **active version**: the only one offered to users. Publish with "Make active after publishing" (ticked by default; the first release of an add-on is always activated automatically), **Make active** on any eligible release (older ones too = rollback), **Automatic (newest)**, and **Restore previous selection**. Yanking the active release withdraws the selection: users are offered nothing until you choose again. Restoring a yanked release never activates it.
* Pure logic: `addon_logic.js`; test: `node --test test/addon_logic.test.js`.
* **Add-on manager list (Step 2.1, needs migration 0014)** - the top of the Add-ons tab shows every add-on from `admin_list_addons()`: name, id, feature key, release / yanked / deleted counts, latest version, what users are offered now, and whether it has a registry record. On a server without 0014 the panel says so, has no create/edit controls, and the rest of the tab works as before. Optional browser check (needs Playwright, uses a stubbed server, no database): `node test_ui/addon_manager_list.smoke.js`.
* **Create / edit add-on name and description (Step 2.2, needs migration 0014)** - `New add-on` and a per-row `Edit` (`Register` for an add-on that has releases but no record yet) open a form that calls the real `admin_upsert_addon(p_addon, p_name, p_description)`. Rules mirrored from the function: id `^[a-z0-9_]{1,32}$` (fixed once created), name 1-80 characters, description 0-400 characters, all after trimming. `admin_upsert_addon` is an upsert and would silently overwrite an existing id, so the form refuses an id that is already in the list and re-reads `admin_list_addons()` right before saving. Only name and description are written; no release, selection, Storage object, signing or forced-update setting is touched, and the record does not add the add-on to the app. After a save the Add-ons tab is reloaded. Optional browser check (stubbed server, no database): `node test_ui/addon_manager_edit.smoke.js`.
* **Version history and release selection (Step 2.3)** - the Add-ons tab has a `Version history` card (pick an add-on, or press `Versions` in the manager list): every release newest first with version, state, seq, size, SHA-256, publish time and app-version range. States: **Active** (chosen by an admin), **Offered** (what users get right now, also for Automatic), **Yanked**, **Previous selection**; **Withdrawn** is shown for the add-on as a whole (users are offered nothing). Buttons call the EXISTING functions only: Make active `admin_set_addon_active`, Automatic `admin_clear_addon_active`, Restore previous selection `admin_restore_previous_addon_active`, Yank / Restore `admin_yank_addon`, and Deactivate `admin_withdraw_addon` (needs migration 0014). The revision read from `admin_get_addon_selection` is sent as `p_expected_revision`; a `stale:` refusal reloads the tab. `admin_yank_addon` takes the same optional `p_expected_revision` since migration 0017 (Step 8; prepared, not yet applied - apply it before deploying this Admin build; Yank / Restore send the revision only when the add-on has a selection). No package download, replacement or deletion (Steps 2.4 / 2.5).
* **Package download and replace (Step 2.4)** - every row of the `Version history` card has `Download` (a signed Storage link that expires after 60 seconds, created with the admin's own session) and `Replace package`. Replace is offered only for a version that is neither the active (pinned) nor the currently offered one (the server checks again) and needs migration 0014 (`admin_replace_addon_release`). You choose the rebuilt `.mzaddon` and its `release.json`; size and SHA-256 are computed in the browser and must match `release.json`, which must describe the same add-on, version, seq, channel, feature key and app-version range. The panel then keeps a copy of the package that is stored now, uploads the new file over the same path, and records the new size and SHA-256 (with the old SHA-256 as `expected_sha256`). A yanked release stays yanked. If the database step fails after the upload, the window explains that Storage and the database disagree and offers Retry database step / Restore previous package / Save a copy. PCs that already installed that version keep their old files: publishing a new version is the safer practice. No delete action.
* **Delete version / delete add-on (Step 2.5)** - every row of the `Version history` card has `Delete` (`admin_delete_addon_release`; disabled with the server's reason for the active (pinned) or currently offered version, the server checks again) and every row of the add-on manager has `Delete` (`admin_delete_addon`; since Step 2.7 the SERVER refuses a whole add-on while users can be offered it, so the button is disabled with the reason and the server's refusal is explained if the list was stale: press `Deactivate` under `Versions` first). Both need migration 0014. Typed confirmation (the version / the exact add-on id), then the database is changed FIRST, in one server transaction (tombstone, audit entry; yanked versions stay revoked), and only after the server confirmed it the returned package file(s) are removed from Storage with the admin's own session. If the Storage removal fails the window stays open with `Retry Storage clean-up` (repeats ONLY the removal, never the deletion), `Copy file paths` and an explicit `Close without cleaning up`. Deleting a server package does NOT delete copies already installed on users' PCs; only a yanked version makes apps stop it. Deleted version numbers and seqs cannot be used again. Checked with `test_ui/addon_delete.smoke.js` against a stubbed client (SQL and Storage are not exercised).
* **Delete guard (Step 2.7)** - `admin_delete_addon` in 0014 refuses to delete an add-on while it is offered (selection not deactivated and at least one non-yanked stable release the catalogue could hand to an app). Static check: `node --test test/delete_guard.test.js`. The SQL cases are in `MetaZone_App/supabase/tests/test_addon_manager.py` (section E2) and have NOT been executed (no PostgreSQL). Migration 0014 is still unapplied: test project first.
* **Pre-publish review (Step 2.6)** - no new feature. It reads text only: it does NOT run the SQL or touch Storage.
